## 一、修了什么

### 1. 预设故障：无法新建会话（用户报的原始问题）

**根因链**（可复现）：

| # | 事实 | 证据 |
|---|---|---|
| 1 | profile 写着 `selectedDefault: redteam` | `profiles/web/cordis.patch.yml` |
| 2 | 但 `cordis.yml` 只声明 standard / ptc / minimal / cordis 四个预设 | 合成配置 dump |
| 3 | `redteam` 唯一来源是插件运行期 `ctx.agentPresets.register()` | `lib/redteam/index.js` |
| 4 | dsh-prompt 的 `package.json` **没有** `./redteam` 导出 | 修复前 |
| 5 | dsh-prompt 的 patch 层 **没有** redteam 那三行 | 修复前 |
| 6 | 预设里的工具行写着 `dsh-purge/redteam/tools`，而 purge 已卸 | 修复前 |

→ 默认预设指向一个**没人注册**的 id → `agentPresets.resolve()` 抛 not-found → 建会话失败。

**修法**（三处补齐）：

1. `package.json` 补 `./redteam`、`./redteam/store`、`./redteam/ui`、`./redteam/tools`
2. `cordis.patch.yml` 补 `dsh-prompt-redteam` / `-store` / `-ui` 三行
3. `lib/redteam/index.js` 的 `renderToolsPackage` 扩成同时认旧名
   `dsh-redteam-mode/tools` 与 `dsh-purge/redteam/tools`，启动时就地自愈

**验证**：真实例上建会话成功；模式下拉出现「红队模式」。

---

### 2. P0：拖拽排序在 UI 上看不出效果

**现场**：拖拽改了 `order`，装配顺序变了，**面板行序纹丝不动**。

**根因**：`lib/prompt-blocks.js` 的 `describe()` 直接吐 config 数组原序，
而装配走 `order` 升序 —— 两条路径口径不同。

**修法**：`describe()` 的 `blocks` 按 `order` 排序，与装配对齐。

**验证**：拖「破甲」到首位后，UI 行序与装配顺序完全一致。

---

### 3. P0：发消息必炸 `Cannot read properties of undefined (reading 'contexts')`

**现场**：这是最重的一条 —— 系统提示词装配链整个断了。

**根因**：`dsh-system-prompt/lib/index.js` 里 `assemble()` 的收尾代码
被替换成了**一个正则字面量**：

```js
// 损坏形态（479 字符一行）
/[ \t]*const transformed = await this\.ctx\.waterfall\(...\);\n[ \t]*if .../
```

方法因此没有 `return`，返回 `undefined`；宿主 `dsh-agent-loop:909`
读 `assembly.contexts` 就抛。

**来源**：上一轮「loom 残留清理」做 `replace → pattern` 反向替换时，
pattern 在清理脚本里是以正则字面量形式存的，写回源码就成了正则而不是代码。
`index.js.loom-cleanup.bak`（14:32 的备份）保留了正确形态，是铁证。

**修法**：把该行还原成上游代码形态。

**验证**：
- 全树扫描 978 个文件，仅此一处，已修
- 修后真实例发消息**成功完成**（"已完成，用时 6 秒"）

## 七、本轮顺带挖出的环境暗伤

上轮「loom 残留清理」用 `replace → pattern` 反向替换，引入了一处**源码级损坏**
（`dsh-system-prompt` 的 `assemble()` 塌成正则字面量）。

**影响面**：那一处让整个系统提示词装配链断掉，所有会话发消息必失败。

**建议**：以后做这类反向替换，**逐条验语法**（本轮已加了全树扫描器 + 回归测试钉死）。
