# 0004 外部探测为空也要缓存，并给 TTL

## 背景

`locateHostForPatch()` 是「装宿主补丁」与状态页的必经之路。本机实测单次 4380ms，
其中 **99.6% 花在三次 PowerShell 外部探测**上（文件系统探测 1331 次合计仅 5ms）：

| 探测 | 耗时 | 命中时的结果 |
|---|---|---|
| `registryInstallDirs` | 514 ms | 非空 |
| `runningOfficialExecutables` | 462 ms | **空** |
| `shortcutOfficialExecutables` | 3738 ms（timeout 15000） | 非空 |

旧代码三处都是同一个模式：

```js
catch { return [] }                       // 失败不缓存
if (result.length > 0) cached = result    // 只有非空才缓存
```

注释里的理由是对的：**客户端可能稍后才启动，永久缓存空结果会导致本进程再也找不到它。**

但代价被低估了：`running` 返回空是 web 端用户的常态，
于是每点一次面板就重付 0.5 秒；而结果为空却不缓存的探测，
在任意机器上都可能是最贵的那一个（本机 `shortcut` 3.7 秒，但 timeout 是 15 秒）。

## 决策与取舍

**选定：空结果进带 TTL（90s）的缓存；失败不进 TTL；非空仍走原永久缓存。**

放弃的方案：

1. **保持原样（空结果不缓存）**
   放弃原因：把「客户端稍后启动」这一种情况（用户主动装桌面版，rare）
   的代价，摊到了「每次打开面板」（every time）上。本末倒置。
2. **空结果也做永久缓存**
   放弃原因：原注释担心的场景会真的发生 —— 用户装完桌面版，重启插件后
   依然提示「未安装」，因为缓存说空。
3. **启动期预热探测**
   放弃原因：会把 4 秒从「点面板时」挪到「宿主启动时」，
   但宿主启动是更敏感的时刻（用户以为 dsh 卡死了）。属另一个取舍，本轮不做。

关键取舍：**模块级永久缓存只存非空结果，空结果只进 TTL 缓存。**
这条最容易被后来者破坏 —— 一旦有人图省事写了 `cachedXxx = result`（空值），
TTL 就永远没机会生效，「客户端后启动找不到」的 bug 会静默回归。
该约束由 `test/probe-cache.test.mjs` 的 TTL 组断言锁住。

## 后果

- 第二次调用 3802ms → **5ms**；`locateHostForPatch` 冷启 4380ms → 509ms。
- **冷启第一次仍慢（约 4 秒）**。这是「枚举本机所有可能安装位置」的固有代价，
  用户只付一次（进程生命周期内）。不去追它 —— 追它要么砍探测范围（漏装），
  要么做启动期预热（拖慢宿主启动）。
- 新增 `probeStats()` / `probeCacheState()` / `setProbeClock()` / `resetProbeCache()`
  四个可观测接口。**探测次数从「不可见的副作用」变成「可断言的状态」**，
  这是本决策最重要的一笔遗产：以后所有关于这块的性能回归都能用
  「spawn 几次」断言，而不是「几毫秒」（后者换机器就失效）。
- 时钟回拨 / NaN 一律按过期处理。否则 age 变负数会让缓存永不过期，
  正好犯下本决策要避免的错。
- `clearDesktopLocateCache()` 现在也清 probeCache —— 用户装完桌面版点「应用」
  时应当立刻重新探测，而不是等 90 秒。
