# 0003 补丁计数收敛到单点，na 计入分母

## 背景

状态页上有**五套**互不同源的补丁计数，各自丢不同的东西。本机实测（develop@f70370d，82 个补丁）：

| 口径 | 来源 | 实测 |
|---|---|---|
| A | `patch_status` 键数 | 82 |
| B | 状态分布 | pending45 / applied6 / skipped18 / na10 / missing_file2 / unmatched1 |
| C | `patches_total`（跳过 na） | 72 |
| D | `display_total`（再折叠成行） | 63 |
| E | 面板本地 `tallyPatches(patchRowsOf)` | 72 |

面板「已清洗 X / 共 Y」的 Y 到底是 82、72 还是 63，取决于读哪个字段。
用户看到 63/82 与 82/82 并存——两个数都「对」，只是量的是不同的东西。

更深一层：**旧算法自己都加不起来**。用真实状态验证：
`applied 6 + pending 45 + skipped 20 = 71`，而 `total = 72`。
它漏统计了 `unmatched`。所以问题不只是「口径不一致」，是旧口径内部就漏项。

## 决策与取舍

**选定：单点 `tallyPatchStatus()` 产出全部分类，约束 `total ≡ 六类之和`，na 计入分母。**

放弃的方案：

1. **让 `patches_total` 继续排除 na（保持 72）**
   放弃原因：这样它和 `patch_status` 的 82 键永远对不上，「哪个是对的」这个问题
   会一直悬着。而 82 才是真实的补丁数。
2. **在面板侧统一（只改前端）**
   放弃原因：后端仍会导出 72，任何直接读 `/status` 的脚本（README 里明确支持
   `curl` 自动化）都会拿到不一样的数。修必须在数据源头。
3. **保留五套口径，但在文档里说明各自含义**
   放弃原因：五个数都「有解释」但互相矛盾，等于把解释成本转嫁给用户。

关键取舍：**na 计入分母，但补丁数也算进「适用分母」**。
这是本轮最容易出错的一处——第一版只做了前半句，结果进度条永远到不了 100%（见后果）。

## 后果

- `patches_total` 恒等于 `ALL_PATCHES.length`（有宿主时）。恒等式由测试断言，不只写在文档里。
- **新增 `patches_applicable = total - na`**。两个分母各有分工：
  - `total`（82）：和 `patch_status` 对账
  - `applicable`（72）：完成度 / 进度条
  混用会导致进度条打满只有 88%，看起来像永远做不完——那是撒谎。
- **无宿主时 total 必须是 0，不是 82**。否则用户看到 0/82 会以为「全都没打上」，
  而真相是「还没找到宿主」。原实现刻意不累加分母，那个意图是对的。
- 面板不再本地 `tallyPatches`，改读后端 `patches_tally`。前端重数是第五套口径的成因。
- **新增硬约束**：任何新的补丁计数都必须从 `tallyPatchStatus()` 派生，
  不许自己 `for` 循环累加。该约束由 `test/patch-tally.test.mjs` 的源码级断言锁住。
