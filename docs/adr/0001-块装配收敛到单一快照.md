# 0001 装配收敛到单一快照

## 背景

块引擎的装配函数跑在**每轮对话的同步路径**上：宿主组装 systemPrompt 时调它。
改造前 `assemble()` 对每个块都单独 `readJson(config.json)` 查内联正文，
于是 N 个块 = N+1 次「读盘 + JSON.parse」，整体 O(n²)。

实测（Windows / Node 22）：

| 块数 | config.json 读盘 | 单次装配 | 每轮对话用户等待（2 次装配） |
|---|---|---|---|
| 7（出厂） | 13 次 | 1.4 ms | 2.7 ms |
| 30 | 56 次 | 4.5 ms | 9.1 ms |
| 300 | 206 次 | 90.1 ms | 180.3 ms |

`describe()` 更糟：307 块时 config 读 616 次、耗时 222 ms，正文被读两遍。

这个退化**不会抛异常、不会让测试变红**，只会让用户觉得"插件越用越卡"。
所以它必须被一条显式约束钉住。

## 决策与取舍

**选定：把"读"收敛成 `loadSnapshot()`，装配 / `describe` / 面板全部吃同一份快照。**

放弃的方案：

1. **给 `readBlockContent` 加进程级缓存（按 mtime 失效）**
   放弃原因：mtime 精度在部分文件系统上只有秒级，同秒内连续保存两次会读到旧正文 ——
   而"改块立即生效"是这个插件的核心卖点，不能拿它换性能。
2. **只缓存 config 的解析结果，正文仍逐块读**
   放弃原因：解决了 O(n²) 但没解决"正文读两遍"（`assemble` 一次 + `describe` 一次），
   而且留下两套读取路径，三档优先级（内联 > override > blocks）容易在两条路上漂移。
3. **异步读取 / worker**
   放弃原因：宿主调 `systemPrompt.section` 的 `text()` 是同步契约，改成异步要动注入层，
   风险远大于收益 —— 而同步读盘本身在 300 块下也只要 15 ms。

关键取舍：**快照是"一次调用内的一致视图"，不是跨调用缓存。**
每次调用重新读盘。这就把"性能"与"实时性"解耦了：不牺牲实时性，也不引入失效逻辑。

## 后果

- 单次装配的 `config.json` 读盘恒为 1 次，与块数无关。300 块 90 ms → 15 ms。
- `readBlockContent` 与快照共用 `pickContent`，三档优先级只有一处实现。
- **新增一条必须遵守的约束**：任何新的批量读取路径都必须走 `loadSnapshot()`，
  不许在循环里调 `readBlockContent()` —— 那会把 O(n²) 悄悄种回去。
  该约束由 `test/reading.test.mjs` 用"读盘次数"断言锁住。
- 性能断言刻意不写死毫秒（换机器就失效），改断"块数 ×10 时耗时不许 ×30"。
