## 一、第一性原理：位置只有两个值得拧

### 1.1 拒绝是一条通路，不是一个决定

模型只做一件事：**给定前缀，逐 token 采样**。
"拒绝"不是"判断了一下然后拒绝"，而是 **"我无法"这几个 token 的概率被前文抬到了最高**。

三个可干预的环节：

| 环节 | 拒绝怎么形成 | 破限能做什么 |
|---|---|---|
| A. 前文里有「要被审查」的信号 | 关键词/句法/题材激活拒绝通路 | 消除信号：换词、包语境、改句式 |
| B. 人格权重低于安全规则 | 模型认为自己是助手 | 抬人格权重：造非 AI 身份 |
| C. 采样第一步落在拒绝 token | 首 token argmax 是「我」 | 预填 / 首词锁定 / 抗截断 |

**结论：破限 = 让「继续写」这条通路在每一步采样上都高于「开始拒绝」。**
所有手法都是在这三个环节上做概率操纵。

### 1.2 位置对模型的唯一意义是注意力曲线的落点

注意力是 **U 型**：两头高、中间塌。

```
消息数组：
[system] [user1] [asst1] ... [userN]
   ↑                            ↑
  顶部                        尾部（紧跟生成点）
 系统提示内部                  消息数组末尾
```

| 位置 | 落点 | 机制 |
|---|---|---|
| **顶部** | U 型左峰 | `systemPrompt.section`（拼进那条 system 消息内部） |
| **尾部** | U 型右峰 | 追加到**本轮请求**的 messages 末尾 |

**「深度」不是第三个位置**，是「离终点峰有多远」的衰减刻度。`depth 0` 在峰上，
`depth 4` 已滑坡，`depth 20` 进谷。所以只做两个档位。

### 1.3 社区实测支撑

| 结论 | 出处 |
|---|---|
| 真实酒馆预设 60 槽 = 58 system / 2 user / 0 assistant，**两个底部槽都是 user** | `tasks\2026-10-15_card-preset-jailbreak-research\线索\预设观察笔记.md` |
| 「规则去尾部，知识去前部」 | `成品\00_总索引.md` §3 |
| 抗截断是第六类破限（愿意写但写一半停 = 等同拒绝） | `成品\04_破限破甲第一性原理.md` §3 |
| 「消息格式不对导致破限失效」是社区共识 | `线索\破限观察笔记.md` §E |
| Lily 做法：破限头（179 字虚构框架）+ 破限尾 + 正则抹痕防自我污染 | `04` §2.B |

```
├─ lib/prompt-blocks.js      ← 【新】块引擎（只读装配侧）
├─ lib/prompt-edit.js        ← 【新】块写入侧（增删改查 / 排序 / 开关 / 出厂）
├─ lib/prompt-inject.js      ← 【新】注入层（section 注册 + 尾部消息构造）
├─ lib/prompt-patches.js     ← 【新】宿主补丁表（尾部注入的唯一落地机制）

```

### 2.1 三层职责

| 层 | 文件 | 纪律 |
|---|---|---|
| **装配（只读）** | `prompt-blocks.js` | 每轮被调用，**必须无副作用**：不写盘、不抛 |
| **写入** | `prompt-edit.js` | 全部走 tmp+rename 原子写；对外只返 `{ok:false,error}`，**不裸抛** |
| **注入** | `prompt-inject.js` + `prompt-patches.js` | 失败一律 fail-open |

## 三、关键决策

### 决策 1：尾部走「请求期追加」，不走 `agent/pre-step`

**这是整个设计最重要的一条。**

宿主 `dsh-agent-loop` 会把 pre-step 返回的 messages **逐条落进持久日志**：

```js
// live 宿主 lib/index.js:1077
if (firstAttempt) for (const message of decision.messages)
  this.session.append("user/message", message, { surfaceOp: "append" });
```

而每轮边界消息来自**持久日志投影**：

```js
// live 宿主 lib/index.js:1278
const boundaryMessages = session.deriveMessages();
```

```
pre-step 返回 tail
  → session.append('user/message', tail)      ← 落盘
  → 下一轮 deriveMessages() 把它投回请求
  → 每轮再追加一条
  → 20 轮 = 历史里 20 份同样内容
```

**后果**：上下文膨胀 + 同段重复 → 指令冗余 → 注意力稀释。

**正解**：在 `buildRequest` 的组装点追加 —— 只进这一轮请求对象，**不写 session log**。

附带收益：请求期数组不落盘 → 不受 `user/message message must have role "user"`
这条**落盘/加载边界**校验约束 → `assistant` 角色也可用（ADR-0004 的限制自动消失）。

**锚点唯一性已实测**：`const boundaryMessages = session.deriveMessages();` +
紧接的 `for (const message of boundaryMessages) {` 在 live 宿主中命中 **1 次**。

### 决策 2：补丁幂等写在 pattern 里，不靠外部守卫

第一版设计用「needle 补丁补标记」，结果**它自己会无限叠**（对抗审查抓到的 bug）：

```js
pattern:  "\t\t// [dsh-prompt] append tail blocks...\n"
replace:  "\t\t// [dsh-prompt] append tail blocks...\n\t\t// [dsh-prompt] strict needle\n"
//         ↑ replace 含 pattern → 每次施加都再插一行
```

**修法**：让 pattern **自消耗**。

```js
// 主补丁：pattern 以 const 开头，replace 以 let 开头 → pattern 不再出现
pattern:  "\t\tconst boundaryMessages = session.deriveMessages();\n\t\tfor (...) {"
replace:  "\t\tlet boundaryMessages = session.deriveMessages();\n...needle...\n"

// needle 补丁：把 marker 后的 `{\n` 一起吃进 pattern，replace 在中间插行
pattern:  "\t\t// [marker]\n\t\t{\n"
replace:  "\t\t// [marker]\n\t\t// [needle]\n\t\t{\n"
```

两条都变成**施加后 pattern 不再匹配** → 重复施加是 no-op。历史遗留的 v1 形态也能被升级一次。

### 决策 3：空 override 是**有效状态**，不回落到默认

dsh-purge 的坑：清空文件会被「永不空串」兜底**覆盖回去**，用户永远无法让一段不发。

本插件：**override 文件存在就以上它为准，即使内容为空**。
要让块回出厂，用「还原」按钮**删掉** override。

```
读优先级：config 内联 content > overrides/<id>.md > blocks/<id>.md
                ↑ 存在即采纳         ↑ 存在即采纳（含空）    ↑ 要求非空
```

### 决策 4：块 id 白名单按 **Windows 文件名**约束

对抗审查抓到：白名单原允许 `:`，但它在 Windows 文件名里非法（备用数据流分隔符），
导致 `rename` **EINVAL**，且异常抛到调用方。

**修法**：

```js
/^[A-Za-z0-9_][A-Za-z0-9_.-]{0,63}$/   // 去掉冒号
+ 不以点结尾                            // Windows 会吃掉尾随点
+ 排除 CON/PRN/AUX/NUL/COM1-9/LPT1-9    // 保留名
```

### 决策 5：写入侧全部包 guard，不裸抛

写盘失败不该炸掉 HTTP handler / 面板 / 工具调用。所有写操作统一返回 `{ok:false,error}`。

**另有半成品防护**：新建块时**先写正文、后写 config**；config 写失败则回滚正文 —
保证「要么都有，要么都没有」，不会留下「有块无正文」的状态。

### 决策 6：不擅自改别人的补丁

宿主上检测到 `[dsh-loom]` / `[dsh-purge]` 标记时，**只在状态里上报**，不删。

理由：删了可能让用户另一个插件失效。面板显示「宿主持有外来补丁：…」，
让用户自己决定。

## 四、⚠ 现场发现：宿主补丁与插件生命周期解耦

调查时发现的真实状态：

```yaml
# C:\Users\WoodMe\.dsh\profiles\web\cordis.patch.yml:62-69
- id: dsh-loom
  disabled: true
- id: dsh-loom-redteam
  disabled: true
```

```json
// C:\Users\WoodMe\.dsh\profiles\web\package.json
// dsh.profile.bundles 里没有 dsh-loom
["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app", "dshmarket", "dsh-purge", "dsh-our-free-model"]
```

但宿主实打实带着 **loom 的补丁标记**：

| 包 | `[dsh-loom]` 标记数 |
|---|---|
| `dsh-agent-loop` | 10 |
| `dsh-hooks-claude-code` | 8 |
| `dsh-hooks-codex` | 7 |
| `dsh-settings` | 6 |
| `dsh-system-prompt` | 6 |
| 其余 20 个包 | 各 1–2 |
| **合计** | **29 个包有 loom 标记；`[dsh-purge]` 标记 = 0** |

**这解释「效果特别差」的现场**：

1. 宿主被 **loom 的补丁**改过
2. loom 插件**没挂载**
3. 于是 `globalThis.__dshPurgeHungPrompt` **从没被注册**（loom 的 `installHungPromptGlobal`
   在 `lib/index.js:252,285,931`，但插件不活）
4. 宿主那行 `typeof globalThis.__dshPurgeHungPrompt === "function"` **永远取到 null**
5. → **注入链在宿主层空转**：补丁在，钩子空

**根因一句话：宿主补丁与插件生命周期解耦。**
补丁写进了宿主文件，插件禁用不撤销补丁，只让钩子失联。

**对 dsh-prompt 的启示**：自己的补丁用独立标记 `[dsh-prompt]`，
状态页**必须能报出外来补丁**，不能假装干净。

## 五、对抗审查结论

三轮对抗式审查，抓到并修掉 **3 个真 bug**：

| # | 攻击面 | 发现 | 修法 |
|---|---|---|---|
| 1 | 幂等性 | needle 补丁的 replace 含 pattern → **无限叠层** | pattern 自消耗 |
| 2 | 路径/文件名 | `:` 在 Windows 文件名非法 → `rename` EINVAL 且**异常外抛** | 收紧 id 白名单 |
| 3 | 原子性 | 新建块先写 config 后校验正文 → 超限时**留下无正文的块** | 先校验正文、先写正文、失败回滚 |

另有系统性防护（审查中确认已具备）：

| 攻击面 | 防护 |
|---|---|
| 目录穿越 | id 白名单 + 白名单外全部拒绝（13 种非法形态实测） |
| 巨型输入 | 每块 512KB 上限；400KB 块装配 **14ms**；300 块 describe **971ms** |
| 竞态 | tmp+rename 原子写；200 次边写边读**零残片** |
| 孤立态 | 数据目录被删 / config 是目录 / 块文件是目录 → **都不抛** |
| 失败注入 | 钩子缺失 / 钩子抛异常 → **请求按原样发出**（fail-open） |
| 消息形状 | 请求期消息不带 id / source（不与持久 Message 混淆） |

## 七、已知限制

1. **宿主版本绑定**：锚点按 `@deepseek-ai/dsh@0.2.0-rc.2` 的 `dsh-agent-loop/lib/index.js`
   真实字节写（含 tab 缩进）。宿主换版本后锚点可能失配 —— 状态页会报「宿主补丁未装」，
   顶部注入不受影响。
2. **尾部需要宿主补丁**：不施加补丁时尾部不进请求（面板能看到装配结果，但发不出去）。
3. **`tailDepth` 不参与排布**：只为兼容酒馆预设的 `injection_depth` 字段而存在。
   导入时保留数据，不对它做任何排序。
4. **`assistant` 角色的尾部块**：机制上可行（请求期不落盘），但**没有被真实模型验证过**。
   建议先用 `user`（与社区实践一致）。
5. **不改 purge**：本插件不删、不改 purge 的任何文件。两层共存时各自注册 section，
   想让位请改 purge 自己的配置。
